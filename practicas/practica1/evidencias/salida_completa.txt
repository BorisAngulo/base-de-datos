── Reto 3 (Análisis de complejidad): 1 millón de registros y 3 condiciones

Java (imperativo):
  Hay que abrir el archivo, saltar la cabecera, partir cada línea,
  convertir texto a número y evaluar if (stock < 10). Con 1 millón
  de registros el programa recorre SIEMPRE las 1e6 líneas (O(n)).
  Tres condiciones distintas (precio, nombre, stock) se traducen en
  más if, más conversiones y más código de manejo de errores. No hay
  índice: filtrar por id también es un barrido completo.

SQL (declarativo):
  WHERE stock < 10 AND precio > 20 AND nombre LIKE '%USB%' describe
  el resultado, no el algoritmo. El planificador puede usar un índice
  en stock, rechazar filas temprano y no tocar el millón de filas
  si hay selectividad. Añadir una condición es una cláusula, no un
  nuevo bucle. El motor reutiliza estadísticas y caché.

Conclusión: el CSV empuja la complejidad a la aplicación; la BD la
absorbe en el motor, una vez, para todos los clientes.


── Reto 4 (Agregaciones): COUNT y AVG en una sola consulta

SQL> SELECT COUNT(*) AS total_articulos, ROUND(AVG(precio), 2) AS precio_promedio FROM producto
  total_articulos  precio_promedio  
  ---------------  ---------------  
  3                38.13            
Equivalente en Java leyendo el CSV:
  int total = 0;
  BigDecimal suma = BigDecimal.ZERO;
  for (Producto p : InventarioCsv.leer()) {
      total++;
      suma = suma.add(p.precio());
  }
  BigDecimal promedio = suma.divide(BigDecimal.valueOf(total), 2, HALF_UP);

Variables extra: acumuladores, contador, control del divisor (CSV
vacío), conversión de tipos y un barrido completo sí o sí. En SQL
el motor hace esa pasada internamente —o usa un índice— y devuelve
dos números. No hay que programar el bucle ni decidir cómo redondear
más allá de ROUND(AVG(precio), 2).

── Reto 3 (Análisis final): Tres casos para CSV y tres para la BD relacional

Archivo plano conviene cuando:
  1. El dataset es un catálogo pequeño, de un solo escritor, que se
     versiona en Git (configuración, lista de códigos, export CSV
     para Excel). No hay cajeros concurrentes ni reglas de stock.
  2. Hay que intercambiar datos entre sistemas heterogéneos: un CSV
     es el mínimo común denominador. La integridad se valida al
     importar, no mientras el archivo viaja.
  3. Un script puntual (carga inicial, evidencia de práctica, log
     append-only) donde abortar a mitad de camino no deja el negocio
     inconsistente, o se puede regenerar desde la fuente.

La base relacional es imprescindible cuando:
  1. Varios cajeros venden a la vez el mismo SKU. Sin lock ni
     transacción, el CSV vende existencias que no hay (Etapa 4).
  2. El dominio tiene reglas (stock ≥ 0, tipos numéricos, PK) que
     deben cumplirse para TODOS los clientes, no solo para el
     programa Java que se acordó de validar (Etapas 1 y 3).
  3. Hay que separar deberes: el auxiliar de bodega actualiza stock
     y no precios; un apagón no puede evaporar 5 unidades a mitad
     de una transferencia; el respaldo debe recrear esquema y datos
     de forma consistente (Etapas 5, 6 y 7).
